## Start here

**One question blocks everything else:**

> Why does a session running through the Hermes **API server** platform not
> surface the skills index?

The `athena-mission-state` skill is installed, `enabled`, and present in
`~/.hermes/.skills_prompt_snapshot.json`. Asked *"do you have skill X"*, an
API-server session says **no**. Yet `skill_view(name="athena-mission-state")`
called explicitly **works** and returns the right answer from live DCS data.

So the skill is reachable but not advertised. Find that mechanism and the fix
is probably one config line.

**Already ruled out** (do not re-check):

- OS platform gating — `skill_matches_platform` is about macOS/Linux, not
  Hermes platforms
- Stale snapshot — the skill *is* in `.skills_prompt_snapshot.json` (239 skills)
- Session age — a brand-new `conversation` name behaves identically
- `platform_hints["api_server"]` in `agent/prompt_builder.py:1116` — prose
  guidance, not a gate
- `platform_toolsets` in `~/.hermes/config.yaml` — defines `cli` only; no
  `api_server` entry, and adding one was not tested

**Do not** fix this by naming the skill in the bridge prompt. That was tried
and reverted: loading a skill mid-turn pushed the exchange past the 15 s
timeout, so calls that had been answering in 4.5 s failed with
`hermes unreachable`. See `docs/PITFALLS.md` #9 and #10.

Suggested next probe: instrument what the API server actually passes as its
platform identifier when building the system prompt, and compare against
whatever the skills-index builder expects.

## What works — proven on live radio

| Stage | Evidence |
|---|---|
| Audio in | peak −1 dBFS, quiet floor `0.00000`; SRS effects proven RX-side |
| Admission | frequency + modulation + speaker, observed not trusted |
| Recognition | ~1.0 s, verbatim, consistent across ~30 live calls |
| Persona routing | `athena` / `hermes` resolved; unaddressed calls ignored, 6+ for 6 |
| Bridge | API server, synchronous, `mode=api-server` |
| **Safety gate** | *"Athena, spawn a tank at sector alpha"* → `action_preview` → **suppressed on a live call** |
| Transmit | `mute: true` throughout; nothing ever sent |

**Ownship resolves from live DCS:**

```
player_name: Prometheus · callsign: Dodge21 · A-10C_2 · confidence: high
```

**The skill works when invoked directly:**

> *"You're in an A-10C II (unit type A-10C_2), callsign Dodge21 — resolved with
> high confidence, though note the snapshot's evidence source is a fixture
> rather than live DCS telemetry."*

It even qualified its own provenance unprompted, which is the freshness
discipline behaving correctly.

## What does not work

**Athena answers `state=unavailable` over the radio.** The pipeline is fine;
the agent cannot see its mission-state skill, so it answers from general
knowledge and honestly flags that it has no mission data. The contract is
working — it just has nothing to report.

**The mission-state store is a single stale snapshot.** Nothing refreshes it.
That is why the skill's own answer mentioned a fixture source.
