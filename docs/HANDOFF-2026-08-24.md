## RESOLVED — the skills-index gap

**Cause: the gateway caches its skills index at process startup.**

```
hermes-gateway started:  2026-08-23 20:46:57
skill created:           2026-08-23 21:40:54   <- 54 minutes later
```

The running process had never seen the skill. Nothing platform-specific about
it, and nothing wrong with the API server.

Confirmed by restarting the gateway and asking the same question:

```
before restart (PID 964381):   "Do you have skill athena-mission-state?" -> No
after  restart (PID 1282582):  same question                             -> Yes
```

`skill_view(name=...)` worked throughout because it reads from disk on demand.
The *index* is what was stale.

**Correcting yesterday's ruled-out list:** "session age" was dismissed on a bad
test. A brand-new `conversation` name does start a fresh session, but the
skills index lives on the *process*, not the session. Right instinct, wrong
lifetime.

**Verification that the index itself was always fine:**

```python
from agent.prompt_builder import build_skills_system_prompt
p = build_skills_system_prompt()
assert "athena-mission-state" in p   # True, even while the live process said no
```

**Operational rule: after adding or editing a skill, restart the gateway.**

```bash
sudo /home/pcorajr/.local/bin/hermes gateway restart --system
```

## What does not work

**Athena answers `state=unavailable` over the radio.** The pipeline is fine;
the agent cannot see its mission-state skill, so it answers from general
knowledge and honestly flags that it has no mission data. The contract is
working — it just has nothing to report.

**The mission-state store is a single stale snapshot.** Nothing refreshes it.
That is why the skill's own answer mentioned a fixture source.
